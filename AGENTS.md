# Fake CUDA development guide

Read `README.md` before making changes for the human-facing architecture, scope, and debugging findings. This guide records implementation constraints, configuration, verified behavior, and limitations; the **goals** below are not claims that every feature is already implemented.

## Scope and goals

- The CMake project is named **`fake_cuda`** and produces `libcuda.so.1` as a CUDA Driver replacement. Target **CUDA 13**, while retaining Driver ABI compatibility for CUDA 12 clients, especially versioned symbols and version selection in `cuGetProcAddress`.
- Implement or simulate **only the CUDA Driver API**. Do not add `cuda*` CUDA Runtime API exports. Use the [NVIDIA Driver API categories](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/apis.html) as the reference. ZLUDA may inform the design, but do not copy its code.
- Aim to support PyTorch device discovery and tensor creation on virtual GPUs, memory operations, kernel scheduling, stream/event operations, and graph control flow without physical GPUs. Extend the API incrementally in response to real calls rather than predeclaring everything.
- **This is a timing and control-flow simulator, not a numerical compute engine.** Device allocations return non-dereferenceable virtual addresses; the simulator does not store device data, copy bytes, or execute CUDA kernels. Do not describe successful imports, device discovery, or tensor metadata tests as evidence that numerical operations or model inference work.

## Layout and ABI

- `include/driver_api/` contains public C API headers grouped by Driver API category (such as `context.h`, `stream.h`, `memory.h`, `graph.h`, and `execution_control.h`). `all.h` includes **implemented** categories only. Do not restore `include/api`, `cu_api.h`, `cu_` header prefixes, or abbreviate execution management to `exec`. Add categories only when needed.
- `src/driver_api/common.c` exposes shared C Driver ABI entries and version-aware `cuGetProcAddress` resolution; `cu12.c` and `cu13.c` implement the distinct historical and CUDA 13 ABI signatures, with shared macro-alias handling in `bridge_internal.h`. Match CUDA header signatures, ABI versions, and symbol visibility. When adding an entry point, check both `cuGetProcAddress` resolution and `exports.map`.
- `include/impl/` and `src/impl/` are the **C++23, object-oriented** implementation. Organize code by Device, Context, Stream, Registry, Scheduler, QueueScheduler, VirtualMemory, Capture, Graph, GraphManager, and related responsibilities. `Capture` collects stream/event dependencies; immutable `Graph` definitions own node topology and replay logic; `GraphManager` owns capture sessions and graph/executable handles (executable instances share their graph definition even after the source handle is destroyed). Graph-related C-facing wrappers live in `src/impl/graph.cpp`; the C Driver ABI remains in `src/driver_api/`. Use smart pointers to express ownership, weak references to avoid cycles, and RAII for locking and lifetime management. Never free virtual CUDA addresses or opaque handles as host pointers.
- Put device profiles under `include/profile/`; the GH200 profile is `include/profile/gh200.h`. Do not put new profiles in the implementation layer.
- Use modern, target-scoped CMake configuration. Keep the C ABI bridge built as C and the implementation built as C++23; do not change the project or library names when restructuring targets.

## Device and scheduling semantics

- Virtual GPUs use per-device profiles from `FAKE_CUDA_SYSTEM`, a shared `FAKE_CUDA_PROFILE`, or the captured GH200 default; one device is exposed by default, and `FAKE_CUDA_DEVICE_COUNT=1..1024` can opt into multiple independent devices. Consult `README.md` and `tests/compare_real_gh200.py` for configuration and validation. Do not claim that unmeasured attributes or bandwidth exactly match real hardware.
- Each device owns named **`h2d_queue`, `d2h_queue`, and `compute_queue`** members. Local D2D copies and kernels use the compute queue. Its `p2p_queues[peer_ordinal]` owns each outgoing directed P2P queue; transfers in opposite directions can overlap. Asynchronous calls enqueue operations recording their stream, queue, and dependencies. Preserve in-stream order, cross-stream event and legacy-default-stream dependencies, and overlap between independent queues.
- `cuStreamSynchronize` waits only for work submitted to its target stream, not unrelated streams. Do not hold the scheduler lock while waiting. Account for concurrent submission, other streams completing first, multithreading, and context destruction.
- Follow CUDA's documented stream ordering and dependency guarantees; do **not** treat priority queue + FCFS as real CUDA scheduling. Lower numeric stream priorities are non-preemptive hints for preferentially launching compute kernels when possible, not execution-order guarantees; NVIDIA documents no H2D/D2H priority effect. Cross-stream FCFS and guaranteed concurrency are not CUDA contracts. Clamp requested priorities to the range reported by `cuCtxGetStreamPriorityRange` and return the clamped value via `cuStreamGetPriority`. Label any deterministic resource-queue ordering as a simulator timing heuristic.
- H2D/D2H delay is based on transfer size and configurable virtual bandwidth; local D2D uses configurable HBM bandwidth, while P2P copies use `FAKE_CUDA_P2P_BW_GBPS` (an unmeasured simulation parameter). Defaults and units are recorded below. These delays do **not** imply a real byte copy. The default `SyntheticConstant` kernel provider preserves **10 ms** of virtual work.
- Support synchronous/asynchronous virtual allocations, stream capture/replay, and event dependencies within graphs. Return appropriate errors for unsupported cases; never return unconditional success merely to let a framework continue.

## Current implementation and calibration

- `PerformanceModel` is an internal C++ batch interface, accessed under the scheduler mutex; providers must not reenter Driver calls. Only kernel/device-service results are admitted. `MeasuredReplay` uses explicit process-local bindings and finite ordered samples, not an automatic calibrated code cache. Unknown argument layouts, mismatches, exhausted samples and unsupported accounting scopes fail. Query before mutating graph timelines; reuse the same predictions for preflight/submission and commit the cursor/service ledger only after success. Capture does not query or charge. Keep predictor wall cost out of service durations; host time remains unknown and the paced scheduler is not an offline clock. See `perf_model_contract` for rejection, graph atomicity and delay-injection checks.
- `load_measured_replay` imports schema-1 timing files through explicit `ReplayBinding` records. The caller verifies external code/hardware/condition identities; the loader checks those identities, symbol and complete packed launch metadata before constructing a provider. Reject the whole file on any parse/binding/read error. Keep external measurement provenance and sample index on each prediction. Do not auto-bind opaque images by symbol, silently ignore unknown fields, or turn fixture values into calibration claims. `replay_file_contract` covers file-backed eager/graph execution and rejection cases.
- Kernel queries have unique nonzero invocation IDs, assigned anew for each eager call or graph replay. `validate_predictions` requires one result covering exactly its corresponding query; providers must populate `covered_invocation`. The same validator gates the paced Driver and `replay_kernel_trace`. The latter is a fixed, topologically ordered kernel-only diagnostic with explicit host costs and normalized stream/dependency inputs. It models one host lane and one submission-ordered compute queue per device, not live actors or automatic CUDA synchronization. Its target timestamps use only declared costs; replay-call wall time includes query cost. Do not add query and replay-call wall time together, or call this the P4 coordinator. `kernel_replay_contract` validates coverage failures, cross-device dependencies, checked arithmetic and 100× injected query-delay invariance.

- `src/impl/queue_scheduler.cpp` uses the per-stream tail, event dependencies, legacy default-stream barriers, and each device-owned `ExecutionQueue`'s availability to determine operation start/end times. Kernel, local D2D, and memset share `compute_queue`; `p2p_queues[peer_ordinal]` serialize each outgoing ordered device pair, allowing opposite directions to overlap in the model. Resource queues are **not** CUDA streams and are not a measured count of hardware engines. This approximation may overestimate independent copy/P2P bandwidth or underestimate concurrent kernel execution.
- `FAKE_CUDA_H2D_BW_GBPS=358.0` and `FAKE_CUDA_D2H_BW_GBPS=296.2` are defaults based on a **single** 128 MiB × 10 pinned-buffer GH200 measurement on this host (CPU/memory NUMA bound). They are workload-dependent observations, not guaranteed bandwidth. The published GH200 NVLink-C2C reference limit is 450 GB/s per direction (900 GB/s bidirectional aggregate), **not** measured memcpy throughput. `FAKE_CUDA_HBM_BW_GBPS=4800` and `FAKE_CUDA_P2P_BW_GBPS=50` are unmeasured modeling defaults. All bandwidth variables use decimal GB/s; delay is `bytes / (GB/s × 1e9)`. `tests/benchmark_real_bandwidth.py` and `tests/compare_real_gh200.py` require a **real GH200** and must not be interpreted as fake-driver numerical tests.
- Device 0's captured profile (`include/profile/gh200.h`) reports `NVIDIA GH200 144G HBM3e`, 153008209920 bytes of Driver memory, compute capability 9.0, 132 SMs and 60 MiB L2, with captured attributes 1–148. Legacy configuration replicates the selected profile with synthetic all-to-all peer access. `FAKE_CUDA_SYSTEM` supplies per-device profiles and a complete directed direct-access matrix; it excludes the legacy profile/count variables. UUIDs remain synthetic and unique by ordinal. Direct access and transfer-route/bandwidth modeling are separate: the matrix controls query/enable, while peer-copy queues retain heuristic timing. Invalid `FAKE_CUDA_DEVICE_COUNT` values return `CUDA_ERROR_INVALID_VALUE`.
- `cuGetProcAddress` selects the CUDA 12 `cuCtxCreate_v2` ABI vs. CUDA 13's four-argument `cuCtxCreate_v4`. CUDA Runtime's private `cuGetExportTable` UUID/integrity handling is isolated in `src/impl/private.cpp`, undocumented and version-sensitive; unknown private tables fail. Revalidate against new Runtime releases rather than assuming ABI compatibility.
- The scheduler is intentionally process-lifetime to survive CUDA Runtime `atexit` teardown. Opaque handles are borrowed identities; virtual addresses are not host pointers. Context retirement prevents new submission and waits for scheduled work. Current-context lookups use thread-local state and an atomic retirement flag; scheduler mutations still take one mutex (not a lock-free executor). Completed operations and freed allocations are reclaimed incrementally.
- Supported graph tests include virtual D2D/event capture and replay, plus PyTorch 2.13 copy/vector-add capture with four replays. Executables serialize their own launches across streams using a retained completion token. Capture-mode exchange is thread-local; prohibited synchronous allocation/free and stream/context synchronization invalidate affected captures. Relaxed synchronous allocation is outside the graph. External cross-device event waits and peer copies **during capture**, concurrent captures, and captured async allocation/free remain unsupported. Default-priority kernel nodes accept `USE_NODE_PRIORITY`; nonzero captured priorities and allocation nodes are not modeled. Ordinary `cuStreamWaitEvent` can wait on a different device's event. The Runtime's lazy library kernel loading and graph introspection paths use virtual handles; cubin/PTX images are not parsed; kernel names are retained as identities but not validated against images. Packed launch buffers are copied; unknown kernelParams layouts remain explicitly unsupported for prediction. Peer access is tracked per directed context pair, but general peer pointer use by kernels or ordinary D2D is not modeled.

- `ResourceEngine` is a separate explicit execution API: phase demand/residency, dependency-ready admission, weighted capacity sharing and generation-checked completions. Retain completed records for dependency/status lookup, but keep active scans independent of completed history. `replay_resource_trace` preserves predictor coverage/atomic commit while allowing ready work to overtake blocked submissions. It does not replace the live Driver queue scheduler. `Topology` uses explicit global node/device identities, process-local visibility and shared physical-link capacities; ring/flow timings remain declared analytical inputs.
- `adapters/vllm` is qualified U1 for vLLM 0.30.0: original Scheduler/KVCacheManager, fixed-length token oracle and explicit actor delivery. Accept only whole-step costs that already include host/communication; never install them as kernel predictors or charge included NCCL again. Mixed or heterogeneous steps, async/chunked/prefix/speculative paths are unsupported. Native llm-d/Dynamo policies remain separate. AIS runs in its own pinned environment and fails unsupported estimates rather than silently falling back. See `adapters/README.md` and the serving reports for exact versions and capabilities.
- Scheduler pickles must contain trusted metadata only. Shallow-copy `VllmConfig`/compilation configuration and clear `static_forward_context` before saving; worker attention modules carry GPU storage. Verify the retained digest before loading. Freeze both step interpolation and AIS fitting before reading validation data. Include interpreter imports, fit, IPC and natural teardown when claiming complete-process speedups; report reuse-calibration exclusions explicitly. CPU adapters assert no CUDA initialization, but that assertion is not a no-GPU-container proof.
- The no-kill runner `tests/integration/tooling/run_contracts.py` executes CTest-registered commands directly without timeout termination. Use it when the user's process-lifetime constraint excludes CTest's timeout machinery; subprocesses close through EOF and wait naturally.

## Iteration and verification

For kernel timing calibration, retain the actual cubin hash and generating toolchain evidence, not only symbol names or the system CUDA version. Native `inspect_compiled_kernel.py` queries resources and `cuFuncGetParamInfo` without launching kernels; parameter descriptors may be large by-value objects. NCU kernel-replay/cache/clock settings are part of measurement identity. Do not feed host/CUDA-event intervals collected under NCU into device-service samples. The 2026-09-30 compiled-kernel report records real examples of same-symbol/different-cubin variants and separate quantization/GEMM accounting.

`probe_ncu.py` captures/imports NCU reports into schema-1 `isolated_kernel_observations` artifacts, copying the compiled image and retaining report/code/hardware/condition digests. A declared prebuilt image is not proof of runtime module association; CuTe capture requires one variant per command and saves the actual generated PTX/cubin. `replay_probe` uses the core replay engine per observation, preserving unknown parameters and excluding uncollected host/dependency time. Do not route this restricted provider into general Driver submission or call selected samples a complete execution trace. `probe_contract` checks decimal units, malformed inputs and artifact-to-core replay without GPUs.

For accuracy evaluation, freeze calibration before new captures and keep report identities disjoint. `evaluate_probe.py` measures frozen-duration reuse with exact code/hardware/launch/resource keys; it does not infer argument equivalence or install a live predictor. Audit inputs and capture settings explicitly, report unmatched coverage alongside conditional error, and never fit on validation samples. `probe_accuracy_contract` checks scoring, unsupported configurations, source leakage and changed report digests.

Record **nontrivial debugging discoveries and conclusions** in the `README.md` Debugging findings section when evidence establishes them: state the symptom, actual cause or verified observation, resolution or remaining blocker, and scope of validation. Update existing entries rather than accumulating duplicate or speculative notes. Keep the explanation concise and human-readable; leave implementation details, command inventories, and agent instructions here or in the relevant test documentation. Do not describe an unverified inference as a confirmed root cause or a passing import/metadata probe as numerical correctness.

1. Start with **actual failures** from PyTorch, vLLM, or SGLang: distinguish a missing Driver symbol, incorrect behavior of an implemented symbol, a CUDA Runtime/other NVIDIA library or NVML dependency, and a Python package problem. `FAKE_CUDA_TRACE=1` logs `cuGetProcAddress` lookups; `FAKE_CUDA_TRACE_CALLS=1` logs calls to implemented entry points. A `no` in PyTorch's bulk symbol prefetch does **not** by itself justify implementing that symbol.
2. Add a Driver API only when its semantics can be modeled reasonably. Update the C entry point, C++ implementation, resolver table, and targeted tests together; preserve thread safety and the existing ABI.
3. Test in Docker **without GPU devices**, using `--runtime=runc --network=none`; running directly on a GPU host is not equivalent. Use separate uv environments for PyTorch CUDA 12.8/13.0, vLLM, and SGLang. Do not overwrite `.venv-cu*`. Check disk space before installing large dependencies; use a writable data disk for environments and cache if needed.
4. Common regression commands:

   ```sh
   cmake -S . -B build
   cmake --build build -j4
   ctest --test-dir build --output-on-failure
   bash tests/run_no_gpu.sh all
   bash tests/run_no_gpu.sh all tensor
   bash tests/run_no_gpu.sh all memory
   bash tests/run_no_gpu.sh all streams
   bash tests/run_no_gpu.sh all graph
   bash tests/run_no_gpu.sh all multidevice
   # Framework probes require the absolute path to an installed uv venv
   # that Docker can mount read-only:
   bash tests/run_framework_no_gpu.sh sglang /path/to/sglang-venv
   bash tests/run_framework_no_gpu.sh vllm /path/to/vllm-venv
   ```

- Setup: Linux aarch64, `/usr/bin/python3.12`, `uv`, CMake, compilers and local Docker `ubuntu:24.04`. Run `bash tests/setup_uv.sh` for separate project-local `.venv-cu128` / `.venv-cu130` (PyTorch 2.11.0 CUDA 12.8 and 13.0); the CUDA 13 headers in `.venv-cu130` are CMake's default `CUDA_DRIVER_INCLUDE_DIR`. Override that cache path if using another CUDA 13 header installation or reusing a build tree configured against an old path. `ctest` includes per-API/ABI C++ tests, stream/event/graph/multidevice scheduling and concurrent submission from eight host threads. Docker probes force `--runtime=runc --network=none --pull=never`, no NVIDIA devices and `LD_PRELOAD` of this project's driver; directly running on a GPU host does not validate no-GPU behavior. `tests/run_no_gpu.sh` accepts `cu128`, `cu130` or `all`, optionally `discovery|tensor|memory|streams|graph|multidevice`.
- Framework environments: keep vLLM 0.26.0 and SGLang 0.5.17 in **separate** uv venvs on a disk with enough space, mountable at the same absolute path in Docker; do not overwrite `.venv-cu*`. Observed installation used PyTorch `2.11.0+cu130` in each (`uv pip install --torch-backend=cu130`), plus `torchao==0.17.0` from PyPI for SGLang on aarch64 (`--prerelease=allow` for its other dependencies). See `tests/integration/README.md` for probe stages and the optional local-model startup attempt, which does not run inference. `uv pip check` may flag upstream `nvidia-cusparselt-cu13==0.8.0`'s `manylinux2014_sbsa` wheel tag as incompatible with aarch64; framework imports do not validate that library.
- Observed vLLM import can see the virtual device, but CUDA platform selection is blocked by **NVML** (`pynvml.nvmlInit` requires native NVML/device discovery), outside this Driver-only project. The test-only bypass in `tests/integration/README.md` then exposes missing `cuTensorMapEncodeTiled`: do not dummy-export a hardware TMA descriptor encoder merely to unblock import. SGLang's `Engine` class imports after `cuPointerGetAttribute` support, but model loading and inference have not been verified. Report the stage and cause of external blockers rather than expanding outside the Driver scope. Passing PyTorch tensor metadata and graph probes does not imply device data exists or any numerical work occurs.
